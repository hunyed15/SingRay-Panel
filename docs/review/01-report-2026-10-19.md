## 0. 三句话结论

1. **密钥生命周期的第一道门是假的**:代码里有"对外监听禁止默认密钥"的守卫,但 README 推荐的 nginx 反代部署恰好让这条守卫不触发,我用默认密钥**离线伪造 admin JWT 并成功写库**(`GET/POST /api/*` 均 200)。
2. **产品最核心的两句承诺与实现对不上**:"部署永远不会谎报成功"在回滚路径上是空话(失败仍返回 `rolledBack: true`,实测回滚命令报错被吞);"所有敏感数据 AES-256-GCM 加密落库"不成立(Cloudflare/Telegram 令牌明文入 KV 表并进备份)。
3. **工程骨架是好的,收口是缺的**:纯函数 + golden 快照 + 事务化部署骨架都在,但唯一性/订阅协议矩阵/端口规则分散在 4–6 处各写一遍,`packages/shared` 零引用且枚举已过期——新增一个核心要动 18 个文件、41 处字面量。

## 2. P0(立即处理)

### P0-01 默认 JWT 密钥在"README 推荐的部署形态"下不被拦截,可离线伪造管理员身份

- **结论**:默认密钥时的 fail-fast 只在 `PANEL_HOST` 非 `127.0.0.1/localhost` 时触发;而 README 推荐 nginx 反代到 `127.0.0.1:3000`,该守卫永不触发。用仓库里的默认串 `dev-only-change-me` 即可伪造任意 admin JWT。
- **证据**:`apps/server/src/config.ts:13`(key 来源)、`:35-39`(守卫条件 `!['127.0.0.1','localhost'].includes(PANEL_HOST)`);`README.md:96`(nginx 反代 127.0.0.1:3000);`.env.example:4`(占位符 `change-me-openssl-rand-hex-32` 不在黑名单 `DEFAULT_SECRETS`)。**我亲手执行**:默认环境启动 → 用 `dev-only-change-me` HS256 自签 → `GET /api/servers` = **200**,`POST /api/servers` = **200**(见附录 A-1)。
- **影响**:漏配一个环境变量、或直接 `cp .env.example .env` 的公网实例 = 无鉴权 admin;拿到 admin 即可经 deploy/install/port-forward 在全部受管机上执行命令。
- **建议**:守卫与监听地址解耦——`[jwtSecret, appSecret]` 命中 `dev-only-change-me` 或以 `change-me` 开头即拒绝启动;`.env.example` 占位符纳入黑名单。
- **复核**:附录 A-1 的三条命令。
- **置信度**:确认(主审查员实测)

### P0-02 首次启动无条件创建 `admin/admin888`,同样没有守卫

- **结论**:`PANEL_ADMIN_PASSWORD` 缺失时固定口令 `admin888`,并把明文口令打进 stdout;`config.ts` 的弱密钥守卫完全不覆盖口令。
- **证据**:`apps/server/src/services/users.ts:43-48`;`apps/server/src/config.ts:35-39`(只查两个 secret);`apps/server/src/routes/api.test.ts:33` 已把"默认口令可登录"固化成测试事实。
- **影响**:新装实例在公网被扫到默认口令后直接拿到全部机器 SSH 控制面;日志里的明文口令还会进 journald。
- **建议**:对外监听且未设 `PANEL_ADMIN_PASSWORD` 时拒绝启动;或首启随机生成并强制登录后改密。
- **复核**:`Select-String -Path apps\server\src\services\users.ts -Pattern "admin888"` + 公网环境下 `POST /api/auth/login {admin,admin888}`。
- **置信度**:确认

## 3. P1(高优先)

### P1-01 四条命令注入链:自由文本进 shell / 进 systemd unit(socat 可持久化)

- **结论**:`server.name`、`server.client_host`、转发落地地址被裸插值进远程命令与 unit 文件,单引号/分号即可越出参数进入命令位;`sudo` 包装只转义外层 `sh -c`,对已拼好的内层串无效。
- **证据**:`core/ssh/executor.ts:94-97`(仅外层转义)、`:165-170`(`install -m 600 '${stage}' '${remotePath}'`);
  - 路径源:`services/deployAll.ts:77-78`(`certPath: /etc/sing-box/tls/${row.name}.crt`)← `routes/servers.ts:14`(`name: z.string().min(1)`)
  - 健康检查:`core/healthcheck.ts:66-74`(`F=/etc/singray/certs/${domain}/fullchain.pem`)← `client_host`,且调度器每 5 分钟自动触发(`index.ts:110-113`),注入无需点击
  - 转发:`core/forward/index.ts:79`(含冒号直接当 IP,跳过 DNS 校验)、`:107-110`(iptables `--to-destination [${ip}]:${port}`)、`:139-147`(socat unit 文本)、`:156`(写 `/etc/systemd/system/singray-fwd-*.service`)
  - 证书:`core/certs/acme.ts:96,106,155`;`routes/lifecycle.ts:90` 只排除"纯 IPv4 或含冒号"

- **复核**:`Select-String -Path apps\server\src\core\healthcheck.ts -Pattern 'certs/\$\{domain\}'`;`sh -c "F=/etc/singray/certs/a.com; touch /tmp/hc-pwn; #/fullchain.pem"` 后看 `/tmp/hc-pwn`。
- **置信度**:确认(代码路径 + 安全审查员用真实函数跑出的 argv/unit 文本)

### P1-02 回滚"尽力而为"却无条件上报 `rolledBack: true`

- **结论**:备份步骤 `cp … || true` 永不失败,回滚的两条命令全部 `.catch(()=>{})`,而返回结果无论回滚是否成功都写 `rolledBack: true`,steps 里也没有任何回滚结果。README 的"部署永远不会谎报成功"在回滚路径失效。
- **证据**:`core/deploy/index.ts:86`、`:94-97`、`:119`、`:141`;`:88`(`install` 就地覆盖,非原子);`README.md:23`。
- **影响**:首次部署无 `.bak`、或回滚时 SSH/restart 再失败 → 机器停在坏配置或根本不运行,而 UI 说"已回滚",管理员因此不去人工救火。
- **建议**:回滚后重跑同一 `is-active` 探测,`rolledBack = 回滚后状态`;备份失败即判部署失败;swap 改 `install tmp.tmp && mv -f`。
- **复核**:附录 A-2 的探针(输出 `STEPS…health-fail`、`ROLLBACK_FAILURE_VISIBLE_IN_RESULT: false`)。
- **置信度**:确认(主审查员实测探针)

### P1-03 单机部署失败在前端完全静默(死代码 state)

- **结论**:单机/单核心部署结果写进 `deployResults`,但该 state 从未被渲染,`DeployResultModal` 组件全仓 0 引用;失败分支没有任何 `message.error`。
- **证据**:`apps/web/src/pages/ServersPage.tsx:52`(声明)、`:85`/`:101`(仅 set)、`:86-87`/`:102-103`(仅成功时提示);`apps/web/src/components/DeployResultModal.tsx:12`(定义处,无消费者);`routes/deploy.ts:79-83`(200 + 结果对象)。
- **影响**:用户点"部署"后界面无任何变化,`error`/`steps`/`journal`/`rolledBack` 全部丢弃,无法判断失败在哪一步。
- **建议**:失败也打开结果弹窗(组件已写好);最小改法 `if(!ok) message.error(...)`。
- **复核**:`Select-String -Path apps\web\src -Pattern 'DeployResultModal' -Recurse` → 仅定义处。
- **置信度**:确认(主审查员 grep 复核)

### P1-04 Cloudflare / Telegram 令牌明文落库并进备份

- **结论**:其余 4 类凭据(SSH 私钥、节点凭据、Reality 私钥)都走 AES-256-GCM,唯独 CF Token 与 TG Bot Token 以明文写入 `settings` KV 表,而备份是整库文件拷贝(无加密)。
- **证据**:`apps/server/src/services/settings.ts:95-97`;`db/migrations/0001_init.sql:120`(`CREATE TABLE settings (key TEXT PRIMARY KEY, value TEXT NOT NULL)`);`core/backup.ts:37`;与 `README.md:5` 的承诺相反。
- **影响**:一次备份泄漏/旧盘残留 = 可改全部域名 DNS(进而签任意证书)的 CF Token 与 TG Bot Token 全裸,而运维会误以为"备份里的东西都是加密的"。
- **建议**:复用 `encryptSecret` 存这两项;备份文件标注"含全部凭据"并 `chmod 600`/加密。
- **复核**:运行后 `select key, substr(value,1,12) from settings` 直接看到 token 前缀。
- **置信度**:确认(主审查员读码复核)

### P1-05 拓扑同步:期望集键比 DB 唯一约束宽 → 必然 UNIQUE 冲突,且被空 catch 吞掉

- **结论**:期望规则去重键含 `landingServerId`(`entry|port|landing|targetPort`),而 DB 约束是 `UNIQUE(entry_server_id, entry_port)`。两台落地机存在**同号端口**的节点时,同一入口机的两条规则端口相同 → 第二条 INSERT 抛错。INSERT 在 `try` 之外,`recordRun` 在其后;触发器的 catch 是空的且注释谎称"已记录在 job_runs"。
- **证据**:`core/topology/plan.ts:147` vs `db/migrations/0009_topology.sql:24`;`core/topology/sync.ts:56-61`(INSERT 在 try 外)、`:76`(recordRun);`core/topology/trigger.ts:31-33`(空 catch);跨机同端口不校验:`services/ports.ts:32-45` 只查同机。
- **影响**:此后每次自动同步都停在同一行 → 新节点的中转规则全部不再生成,面板零提示(只有拓扑预览的 `toCreate` 长期不为 0)。
- **建议**:期望集键改成与 DB 同口径 `(entryServerId, entryPort)`,冲突产出 skipped 原因;`trigger.ts` 的 catch 补 `recordRun(db,'topology',false,err)`。
- **复核**:`:memory:` 灌 11 个迁移 → 1 relay + 2 landing + 两条 `entry_port` 相同的规则 → 观察 `UNIQUE constraint failed: port_forwards.entry_server_id, port_forwards.entry_port`。
- **置信度**:确认(审查员用真实迁移 + node:sqlite 复现)

### P1-06 同一台机器可被并发操作(部署/安装/健康检查无按机互斥)

- **结论**:唯一互斥只覆盖"部署全部"这个内存 job;单机部署、核心安装、周期性健康检查/流量采集都不拿锁。
- **证据**:`routes/deploy.ts:42-45`(只有 `/all` 查 job)、`:79-83`(`/:id` 无检查);`routes/lifecycle.ts:19-31`(install 无锁);`services/deployAll.ts:297-313`(3 worker,无按机锁);`index.ts:110-119`(健康检查/流量每 5 分钟并发 SSH)。
- **影响**:两路交错 → 后者覆盖前者 `.bak`,回滚把"对方刚换上的配置"当旧配置恢复;install 会把 config.json 覆写成最小配置 → 机器只剩空入站。
- **建议**:按 `serverId` 的 `Map<number, Promise>` 锁,deploy/install/healthcheck 共享,拿不到返回 409。
- **复核**:`POST /api/deploy/all` 未结束时 `POST /api/deploy/1`(带 Bearer)→ 第二次不是 409。
- **置信度**:确认(代码路径无分支)

### P1-07 删除转发规则:机器侧失败仍删 DB 行并返回 `ok:true`;对账只报告不修复

- **结论**:机器侧删除失败降级为 `log.warn`,随后照样 `DELETE FROM port_forwards`,接口返回成功;reconcile 只产出差异清单,UI 文案却写"机器侧以 DB 为准修复",实际没有修复动作。
- **证据**:`routes/port_forwards.ts:150-163`;`core/topology/sync.ts:27-33`(同类吞错);`core/forward/index.ts:122-126`(`iptables-save … || true`);`apps/web/src/pages/PortForwardsPage.tsx`(对账弹窗只有列表,无按钮)。
- **影响**:孤儿 DNAT/socat 继续转发、入口端口长期被占(下次建规则 409),面板已不可见,只能 SSH 手清;重启后 iptables 规则消失而 DB 仍"存在",再对账也修不回来 → 漂移不收敛。
- **建议**:删除失败返回 409 并保留行(或 `pending_removal` 标记);对账弹窗加"重放缺失/清理孤儿",复用现成 `applyForward`。
- **复核**:入口机手删 `singray:<id>` 规则 → `DELETE /api/port-forwards/:id` 返回成功 → `iptables -t nat -S PREROUTING | grep singray` 仍在。
- **置信度**:确认

### P1-08 备份"看起来成功":坏文件挡住当日重试;WAL checkpoint 静默失效

- **结论**:
  (a) 备份是"先拷贝后校验",校验失败直接抛错,但**坏文件已落盘且文件名带当日日期**,`backedUpToday()` 据此判定"今日已备份",当天不再重试,也没有失败告警,设置页把它当有效备份展示。
  (b) `PRAGMA wal_checkpoint(TRUNCATE)` 的返回值/`-wal` 大小不检查;存在第二个读快照连接时 checkpoint **静默不生效**,拷贝出的 `.db` 缺最近提交,而校验只 `COUNT(*) FROM servers`。
- **证据**:`core/backup.ts:32`(不读返回值)、`:36-42`(先拷后验)、`:45-46`、`:52-54`;`index.ts:103-109`(hour 命中即 return);`core/backup.test.ts:16`(测试库未开 WAL,该路径 0 覆盖);合法并发者 `tools/migrate/src/cli.ts:96`。
- **影响**:最需要备份的那天恰好没有可用备份;静默丢最近写入(可能就是刚建的节点与凭据)。若允许 migrate CLI 对着运行中的库执行,此项升 **P0**(数据丢失)。
- **建议**:改 `VACUUM INTO '<path>.tmp'` → 校验 → `renameSync`;失败 `unlink` + `recordRun(ok:0)` + 告警;`backedUpToday` 只认"最近一次成功的备份"。
- **复核**:附录 A-3(审查员实测:有并发读快照时 `-wal` 仍 12392 字节、备份 3 行 vs 库 6 行)。
- **置信度**:确认(审查员用真实 `runBackupNow` 实测)

### P1-09 周期健康检查把三路信号塞一条命令再按行号解析 → 状态错位误报

- **结论**:`systemctl is-active X || echo inactive` 在单元非 active 时**输出两行**,导致后续 `xray` 状态与证书到期日被错位读取;`ping_status` 只记录 SSH 可达,不代表线路可用。
- **证据**:`core/healthcheck.ts:67-74`(`split('\n')` 按下标取 `[sb, xr, certEnd]`)、`:112-117`(只写 ssh 状态)。
- **影响**:任一次核心停止/卸载后,面板开始误报"xray 已停止"、证书临期漏报;首页"在线"只等于 SSH 通。
- **建议**:拆成 3 条独立 exec 逐条解析;核心状态单独落列。
- **复核**:`systemctl is-active sing-box || echo inactive; systemctl is-active xray || echo inactive; echo no-cert` → 输出 3–4 行,对照 `:72` 的解构。
- **置信度**:确认(代码 + shell 语义)

### P1-10 `.env` 根本不加载:README 的首次运行步骤是死指令

- **结论**:`cp .env.example .env` 在 README 里是指令,但仓库没有 dotenv,dev/test 脚本也没有 `--env-file`,`.env` 从不生效。用户以为密钥已配,P0-01/P0-02 因此更容易发生;而之后真配上密钥,已加密的凭据全部解不开(无重加密路径)。
- **证据**:`README.md:65`;`apps/server/package.json:8`(`tsx watch src/index.ts`);全仓 `dotenv|env-file` 0 命中(主审查员复核);`apps/server/src/config.ts:13-15`;唯一的 APP_SECRET 变更警告只写在迁移场景(`README.md:110`)。
- **影响**:从文档照做的人,得到的是一个用默认密钥 + 默认口令运行、且随时会因改密钥而丢凭据的面板。
- **建议**:dev 脚本加 `--env-file=../../.env`;启动日志/首页 Banner 显式标注"当前使用默认密钥/默认口令";提供 re-encrypt 命令。
- **复核**:`Select-String -Path apps,packages,tools,package.json -Pattern 'dotenv|env-file' -Recurse` → 0 命中。
- **置信度**:确认(主审查员复核)

### P1-11 手工转发规则的 `target_port` 不随节点改端口更新

- **结论**:改节点 `listen_port` 只更新 `nodes`,`port_forwards.target_port` 全仓没有任何 UPDATE 写点;自动对账只看 `auto=1` 的行。
- **证据**:`services/nodes.ts:271-275`(只改节点);全仓 `UPDATE port_forwards` 仅 `include_in_sub`(`routes/port_forwards.ts:134`)与迁移;`core/topology/plan.ts:307`(diffRules 只读 auto=1);订阅按 `pf.entry_port` 出线路(`services/subs.ts:97`)。
- **影响**:用户看到"已启用且在订阅里"的线路,客户端连上对端无监听;重新部署也修不好。
- **建议**:改端口时同事务 `UPDATE port_forwards SET target_port=? WHERE target_node_type=? AND target_node_id=? AND auto=0`。
- **复核**:建规则 → 改节点端口 → `GET /api/port-forwards` 的 `target_port` 仍是旧值。
- **置信度**:确认(主审查员 grep 复核)

### P1-12 自适应订阅的 Clash 分支静默丢 Hysteria2

- **结论**:Clash 渲染器按 `case 'hysteria2'` 匹配,而节点表存的是 `hysteria`,落入 `default → null` 被过滤掉,无任何提示。
- **证据**:`core/subscribe/clash.ts:102` vs `services/templates.ts:9`;`:114-115`(`default: return null`);`routes/sub.ts:41-43`。
- **影响**:Clash/mihomo 用户订阅里少节点且无报错,反复怀疑"节点没建成功";同一 slug 三个端点内容不同且无对照。
- **建议**:补 `case 'hysteria'`;订阅响应头/设置页显式列出"本次排除 N 个节点"。
- **复核**:`npx tsx -e "…clashProxy({protocol:'hysteria'…})"` → 输出 `null`(审查员实测)。
- **置信度**:确认

### P1-13 「一键添加」绕过可达性判断,生成"成功但连不通"的线路(本轮新引入)

- **结论**:批量创建不检查 `ip_stack`,不排两跳,直接给每台入口机建"直达落地机"的规则;与拓扑引擎在同一场景下的决策相反。
- **证据**:`services/forwardBatch.ts:233-240`(直接取 `landing.client_host||landing.host` 下发,无 `canReach/resolvePath`)vs `core/topology/plan.ts:86-102`;`core/forward/index.ts:139-140`(v6 目标写 `TCP6:`)。
- **影响**:v4-only 入口机 × v6-only 落地节点 → 接口返回 `created:1`、机器上 `singray-fwd-*` 已 enable,但 socat 永远连不上;拓扑页同一节点显示的是两跳。用户得到一条**显示成功、实际不通**的线路且无任何提示。
- **建议**:`planBatchForward` 内复用 `canReach`:入口不可达且非双栈 → `action:'skip'`,原因写明"需经双栈机两跳,请用拓扑自动规则"。
- **复核**:造 v4-only 中转 + v6-only 落地 → 一键添加 → `systemctl status singray-fwd-*` 起不来而 UI 报成功。
- **置信度**:确认(代码路径;上一轮我以"目标解析在 apply 时才发生"为由跳过了这项检查,结论是错的:解析会成功,但连接不会)

### P1-14 「一键添加」预览端口 ≠ 实际创建端口(入口机无白名单时)

- **结论**:无白名单时预览与创建各自 `randomFreePort`,两次请求独立重算;前端在预览后仍可改选,而"创建 N 条"用的是旧 plan 的条目数。
- **证据**:`services/forwardBatch.ts:174-176`;`routes/port_forwards.ts:124,127`(两个独立请求各自重算);`apps/web/src/pages/PortForwardsPage.tsx`(预览表与创建按钮的状态未联动)。
- **影响**:实测同一份数据三次计划得到 `[24654,44524]` / `[64092,37180]`,实际创建 `[62368,51798]`。用户按预览端口放行防火墙或告知客户端 → 必然对不上。
- **建议**:无白名单也改确定性分配(按 key 派生),或预览明确标注"端口以创建结果为准"并在改选后清空预览。
- **复核**:对一台无 `port_allow` 的入口机连续调用两次 `planBatchForward` → 端口不同。
- **置信度**:确认

### P1-15 多台同段 NAT 机器:全局唯一端口把总容量压成"端口数",且报错指向错误对象

- **结论**:分配用 `globallyUsedPorts`(跨机 UNION)去重,而 NAT 服务商通常给每台机器同一段端口;于是 A 机用满后,B 机(0 个节点)也报"该机器的可用端口已用尽",文案还把原因归给"该机器"。
- **证据**:`services/ports.ts:105-117`(全局集合 + `:110-115` 文案)、`:52-62`。
- **影响**:实测 A/B 都配 `32679-32681`,A 建 3 个节点后 B 建节点即 400。用户会以为 B 的白名单没生效或面板有 bug;而真实约束是"一个端口号在全链路是全局标识"。
- **建议**:分配先只避让本机已用端口,`(entry,port)` 冲突留给链路层检测;错误文案列出"被哪台机器哪个端口占用";服务器表单注明"同段端口在多机间共享配额"。
- **复核**:两台同段 → 第一台建满 → 第二台建节点 → 400。
- **置信度**:确认(审查员实测 + 代码路径)

### P1-16 落地机白名单越界的存量节点仍进订阅 → 订阅里多一条永久超时的线路

- **结论**:拓扑的端口白名单检查用 `slice(0,-1)` 跳过落地机(因为节点端口是既成事实),于是越界节点照常生成末跳规则且 `includeInSub: true`;界面上只有一句"不会自动改号"。
- **证据**:`core/topology/plan.ts:151-156`、`:230`;该行为被测试固化 `core/topology/plan.test.ts:217-225`;UI 软告警 `apps/web/src/pages/PortForwardsPage.tsx`(拓扑弹窗内)。
- **影响**:给 NAT 落地机补填白名单后,其存量节点(如 40000)未映射 → 所有中转机按 40000 连落地机必然超时,而订阅里这条线路看起来完全正常。
- **建议**:对该类节点把 `include_in_sub` 置 0 并标注"线路暂不可用",或提供"迁到白名单内"的一键动作。
- **复核**:落地机填白名单、其节点在 40000 → 立即同步 → 期望规则出现且"进订阅 ✓" → 客户端连接超时。
- **置信度**:确认(这是上一轮"只告警不改号"取舍的未充分表达的后果)

## 6. 对本次新增功能(NAT 端口白名单 + 一键添加)的结论

> 本节由第 6 名审查员独立复核(未告知实现者意图),主审查员核对代码后并入。**结论:有条件可用,不建议直接多机长期使用。**

### 6.1 合格的部分(值得保留)
