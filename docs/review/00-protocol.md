# SingRayPanel 独立审查协议 v1

> 本文件是**提示词 + 方法学**本体,可复用于后续任何一轮审查。
> 核心纪律只有一条:**每条结论都必须可被第三方用一条命令或一次翻阅复核**。

---

## 0. 角色与立场

同时戴两顶帽子,且**不互相妥协**:

| 角色 | 只关心 | 典型失效模式 |
|------|--------|--------------|
| 资深产品经理(PM) | 为谁解决什么问题、旅程是否闭环、承诺与实现是否一致、范围与取舍是否合理 | 把"功能多"当"产品好";替实现者解释动机 |
| 系统架构师(SA) | 边界与依赖方向、状态一致性、失败模式、安全性、可演进性 | 把"能跑"当"正确";只谈风格不谈故障路径 |

**独立性条款**

1. 只依据仓库里的代码、测试、文档、可执行行为;**不假设任何未写进代码的意图**。
2. 实现者(含上一轮新增功能)的代码与老代码**用同一把尺子**衡量,新代码不享受豁免。
3. 无法确证的问题必须标 `待查` 并给出一条**能证伪它的查询方法**,禁止把怀疑写成结论。
4. 不允许出现"建议加强监控/建议重构/建议补充文档"这类**无定位、无复核方法**的空话。

## 1. 审查范围与基线

- 仓库:`D:\Coding\SingRay`(npm workspaces:apps/server、apps/web、packages/shared、tools/migrate)
- 基线:`git log -1` + `git status --short`(审查必须声明"含/不含未提交改动")
- 运行时事实而非印象:能跑的命令优先于读代码推测

### 1.1 证据采集命令清单(可复制执行)

```powershell
# 规模与热点(哪里最可能藏问题)
git ls-files | Measure-Object -Line
Get-ChildItem -Recurse -File apps,packages,tools -Include *.ts,*.tsx |
  Where-Object { $_.FullName -notmatch 'node_modules|dist' } |
  Sort-Object Length -Descending | Select-Object -First 15 Name,Length

# 依赖方向(server 是否反向依赖 web、core 是否依赖 routes)
Select-String -Path apps/server/src/**/*.ts -Pattern "from '\.\./routes/|from '.*apps/web" 

# 风险模式扫描(逐条人工判读,不靠计数定罪)
Select-String -Path apps/**/*.ts,apps/**/*.tsx -Pattern 'catch\s*\{\s*\}'                    # 静默吞错
Select-String -Path apps/**/*.ts,apps/**/*.tsx -Pattern '\bas any\b'                          # 类型逃逸
Select-String -Path apps/server/src/**/*.ts -Pattern 'db\.prepare\(`'                         # 模板串拼 SQL
Select-String -Path apps/server/src/**/*.ts -Pattern 'exec(Fn)?\(conn,\s*`'                   # 模板串拼 shell
Select-String -Path apps/**/*.ts -Pattern 'TODO|FIXME|XXX|hack'                               # 已知债

# 契约一致性:前端类型 vs 后端返回字段
Select-String -Path apps/web/src/services/types.ts -Pattern '^\s+\w+:'

# 测试与构建现状
npm test ; npm run build ; npx tsc --noEmit --project apps/web
```

## 2. 审查维度与评分锚点

每个维度 1–5 分。**分数必须能由证据反推**,不接受"感觉"。

| # | 维度 | 5 分长什么样 | 1 分长什么样 |
|---|------|--------------|--------------|
| D1 | 产品定位与范围控制 | 范围与目标用户严格对齐,拒绝需求有记录 | 功能无限膨胀,每个协议/机型都加一层组合复杂度 |
| D2 | 用户旅程闭环 | 主要旅程无断点,失败可恢复且状态可解释 | 有断点、有静默失败、状态不可信 |
| D3 | 功能完整性 vs 文档承诺 | README 与实现逐条对得上,差异有说明 | 文档写的能力不存在或行为不同 |
| D4 | API / 数据契约一致性 | 前后端类型同源、错误码稳定、字段命名统一 | 同义字段多套命名、错误码随意、类型靠 `as` 对齐 |
| D5 | 领域建模与模块边界 | 领域规则集中在纯函数、副作用在边缘、依赖单向 | 业务规则散落在路由/页面/SQL 里,互相反向依赖 |
| D6 | 数据一致性与事务 | 状态机明确、迁移可回滚、并发有边界、漂移可对账 | 多写路径各自为政,对账靠人工,约束靠"应该不会" |
| D7 | 失败模式与可观测性 | 失败可定位、可回滚、日志含因果链 | 失败被吞、只报"成功"、日志无法还原现场 |
| D8 | 安全与密钥 | 密钥生命周期完整、最小权限、注入面收敛 | 明文/弱随机/命令拼接/公开面过大 |
| D9 | 可运维性 | 部署/回滚/备份/健康检查闭环且有验证 | 靠 SSH 手搓、恢复流程未验证 |
| D10 | 测试与可演进性 | 关键规则有纯函数测试、回归有守卫 | 只测 happy path、新增协议成本高、无回归防线 |

## 3. 结论分级

| 级别 | 判定规则(满足其一即可) |
|------|--------------------------|
| **P0** | 会导致**数据丢失 / 越权 / 生产停机 / 凭据泄露**,且触发路径在正常使用中可达 |
| **P1** | 明确缺陷或结构性设计债:**有具体触发路径**、当前会误导用户或造成静默不一致 |
| **P2** | 风险或维护成本:当前不发作,但在合理变更下会发作;或显著抬高改动成本 |
| **P3** | 改进建议:不影响正确性,影响体验/效率/一致性 |

**升降级规则**:无法给出触发路径的"潜在风险"最高只能到 P2;能给出一行复现命令的缺陷不得低于 P1。

## 4. 每条结论的强制字段

| 字段 | 要求 |
|------|------|
| ID | `D<维度>-<序号>`,如 `D8-03` |
| 级别 | P0–P3 |
| 结论 | 一句话,主谓宾齐全,可判真假 |
| 证据 | `path:line` 或命令 + 关键输出;**禁止粘贴大段代码** |
| 影响 | 谁、在什么场景、付出什么代价 |
| 建议 | 最小可行改法(不是"重构") |
| 复核 | 一条可复制的命令/步骤,别人照做能得到同样结论 |
| 置信度 | `确认` / `部分成立` / `待查` |

**交叉验证**:所有 P0/P1 由主审查员二次复核后写入报告附录 B;复核为"推翻"的条目必须保留在附录并说明推翻理由(防止下一轮重复提出)。

## 5. 子审查员提示词模板

```
你是 SingRayPanel 的独立审查员,负责维度 <Dn 名称>。

仓库:D:\Coding\SingRay(只读!不要修改任何文件,不要 git 操作)
先读:D:\Coding\SingRay\docs\review\00-protocol.md —— 严格按其第 4 节字段输出。

规则:
- 只依据代码/测试/文档/可执行行为下结论;不假设意图
- 每条结论必须有 file:line 证据;没有证据的怀疑标"待查"并给证伪方法
- 最多 10 条,按级别排序;宁少勿虚
- 严禁"建议加强 X"这类无定位空话

输出:markdown 表格(字段见协议第 4 节)+ 一句话总评(该维度分数 1-5 及理由)
```

## 6. 主审查员的额外职责

1. 跑第 1.1 节的命令,建立**运行时基线**(测试/构建是否真的绿,规模与热点在哪)。
2. 对每条 P0/P1 亲自复读代码、亲自执行复核命令;推翻的要记录理由。
3. 打分卡:10 维分数 + 每维**一条**支撑证据(不允许"综合印象")。
4. 输出"前 10 优先级行动",每条给:改动面、风险、可否今天做完。
5. 明确写出**本轮没验证什么**(避免把审查读成保证)。
